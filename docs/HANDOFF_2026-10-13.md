## Previous cash milestone reference (e5f68af)

### Cash source lifecycle

This is practice/account-level **manual bank-account evidence**, separate from claim remittances,
PMS deposits, posted payments, actual bank verification, settlement and recovered revenue.

- `CashSourceTransaction` holds immutable org/namespace/account/transaction identity. A namespace
  and account keep the same source system/product across transactions.
- `CashSourceEvidence` stores immutable source revisions, exact canonical payload/hash, source
  sequence/version/document, status and amount.
- `CashSourceReview` stores immutable ACCEPT/REJECT decisions, actor/stored role, exact evidence
  binding, previous accepted ID, org ledger counts, preview token and idempotency key/hash.
- Explicit positive `sourceSequence` orders revisions; arrival time, observedAt, UUID and opaque
  sourceVersion do not. Same source event exact replay succeeds; changed record/sequence conflicts.
- Highest accepted sequence is the accepted history state. Only accepted **latest-observed POSTED**
  contributes to a source-account tally. A newer observation makes older accepted evidence STALE
  and excluded, even if the newer observation is rejected. History is retained.
- PENDING/REMOVED/UNKNOWN, stale and unreviewed facts do not contribute. Removal is not a debit or
  refund. Null remains unknown. Original source amount/sign convention is retained; canonical
  amounts use positive credit/negative debit. Account debit summary is a positive magnitude.
- Totals are per source/account, never a cross-account aggregate or verified bank balance.
- Accepted historical non-null pending-transaction references form a scoped undirected identity
  graph. Later null does not erase a link; changed non-null links block. Missing parent IDs,
  siblings, chains and cycles are included. Every proposed ACCEPT status checks the prospective
  component, replacing the candidate's old status. At most one accepted POSTED transaction may
  remain; stale accepted POSTED also fences overlap until explicitly reviewed nonposted/removed.
  More than100 visited IDs returns SOURCE_LINK_LIMIT, never a partial safe result.
- Org tuple writes (`UPDATE Organization SET id=id`) serialize admission, including direct SQL
  and repeatable-read writers, without changing updatedAt. Composite restrictive FKs, parent
  sealing, immutable triggers, role/hash/sequence/prior-ID/ledger checks protect retained facts.
- Fresh preview binds evidence/current accepted/latest sequence and org-wide evidence:review
  counts. Exact review retries bind actor+decision+token+key and return the original result even
  after later changes. Reads, replays and mutations all require scoped audit. Audit failure
  rolls back writes or withholds reads; raw source/Prisma errors never reach the global logger.
- Fixed provenance MANUAL_UPLOAD; bankVerification and settlement UNVERIFIED, even if a caller
  labels its source as a familiar provider. All five routes require stored OWNER/ADMIN/BILLING_STAFF.
- Raw/canonical input64KiB; list/history pages at most100 records and2MiB with cursor traversal.
  `accounts` contains full-account statistics only for tuples represented by returned page items,
  bounding the response. It is not an all-account report. Frontend requests20 per page.
